# RADSAFE — Software Requirements Specification (SRS)

**Version:** 1.0 — Planning baseline  
**Status:** Proposed requirements; implementation and validation are pending.

## 1. Purpose

This document defines the functional and non-functional requirements for the RADSAFE MVP: a web application that creates longitudinal CT examination histories from supported DICOM RDSR files.

## 2. Product perspective

RADSAFE consists of:
1. Frontend web interface (HTML/CSS/JavaScript).
2. Backend REST service (Java 21 + Spring Boot).
3. DICOM parsing component (dcm4che, subject to PoC validation).
4. Relational persistence layer (SQLite initially).
5. Scientific dose-calculation module.
6. Reference-data and validation support.

## 3. Terminology

- **RDSR:** Radiation Dose Structured Report.
- **CTDIvol:** CT Dose Index volume, typically reported in mGy.
- **DLP:** Dose-Length Product, typically reported in mGy·cm.
- **Effective dose estimate:** an estimate calculated using DLP × an applicable conversion coefficient.
- **DRL:** Diagnostic Reference Level; an optimization benchmark for defined examination groups, not an individual patient dose limit.
- **RADSAFE Patient ID:** internal identifier generated by RADSAFE.
- **Source Patient ID:** identifier supplied by a source institution/DICOM object.

## 4. Functional requirements

### FR-01 — Upload
The system shall allow an authorized user to select and upload a DICOM file. The UI shall show upload progress and the processing result.

### FR-02 — File validation
The backend shall validate that the uploaded file is readable and contains a supported DICOM object. It shall identify unsupported files and return a meaningful error without crashing.

### FR-03 — RDSR identification
The backend shall inspect the SOP Class UID and relevant DICOM attributes/content. The CT Radiation Dose SR Storage SOP Class UID is `1.2.840.10008.5.1.4.1.1.88.67`; the implementation must still validate the report's content and supported structure.

### FR-04 — Data extraction
The backend shall extract supported fields, including:
- Source Patient ID and issuer, when present.
- Patient name and date of birth only when required and permitted.
- Study date/time.
- Accession number, if present and permitted.
- Institution and station/scanner information, when present.
- Modality and SOP metadata.
- Procedure/protocol/anatomical region, where reliably represented.
- CTDIvol, DLP, units, and the context needed to interpret each value.

Missing or ambiguous fields shall be represented as missing/uncertain, not fabricated.

### FR-05 — Patient record creation
The system shall generate a unique internal RADSAFE Patient ID when a new patient record is created.

### FR-06 — Patient matching
The system shall search for possible existing records using configured matching evidence. It shall not automatically merge cross-institution records using source Patient ID or patient name alone. Uncertain cases shall require authorized review.

### FR-07 — Examination record
The system shall store each accepted examination as a distinct record linked to one RADSAFE Patient ID. Duplicate upload detection shall use appropriate source identifiers/file fingerprints and must not discard legitimate repeat examinations.

### FR-08 — Dose calculation
The system shall calculate an effective-dose estimate only when the required DLP value, unit, anatomical mapping, and approved coefficient are available. It shall store the coefficient, source/version, calculation timestamp, and warnings used.

### FR-09 — Cumulative history
The system shall calculate the sum of eligible examination-level effective-dose estimates for the selected patient and clearly indicate the time period and included records.

### FR-10 — Patient profile
The system shall display the RADSAFE Patient ID and a chronological list of linked examinations. Direct identifiers shall be hidden or masked by default.

### FR-11 — Examination details
The system shall display source metadata, extracted dose metrics, calculation details, parsing status, and any warnings for an individual examination.

### FR-12 — Dashboard
The system shall provide a summary of records and recent processing activity. Any aggregate metric shall state what records it includes.

### FR-13 — Visualization
The system shall display a chronological dose trend. Charts must distinguish missing values from zero values and avoid implying clinical risk thresholds.

### FR-14 — DRL comparison (later MVP extension)
The system may compare examination dose indicators with a DRL only when the examination is matched to a valid reference category, metric, population, and protocol context. The UI shall label the reference and its limitations.

### FR-15 — Report export (later MVP extension)
The system may generate a patient radiation-history PDF. It shall identify the report generation date, included examinations, units, methods, coefficient references, and limitations.

### FR-16 — Auditability
The system shall record important actions such as upload, match decision, merge, correction, and report generation. The MVP may implement a basic event log, but the data model must allow audit expansion.

### FR-17 — Error handling
The system shall provide actionable errors for invalid files, unsupported reports, missing dose values, ambiguous patient matching, and failed persistence.

## 5. Non-functional requirements

- **NFR-01 Reliability:** malformed input must not crash the application.
- **NFR-02 Traceability:** extracted values must be traceable to source data and parsing rules.
- **NFR-03 Privacy:** minimize identifiers and restrict access to identifiable information.
- **NFR-04 Security:** validate file type/content, enforce upload size limits, avoid unsafe file paths, and protect API endpoints as authentication is introduced.
- **NFR-05 Usability:** core tasks must be understandable to a first-time authorized user.
- **NFR-06 Maintainability:** separate parsing, domain logic, calculations, persistence, and API layers.
- **NFR-07 Portability:** local development shall be reproducible using documented Java/Maven setup.
- **NFR-08 Performance:** show clear processing states; define measurable response-time targets after representative sample files are available.
- **NFR-09 Accessibility:** keyboard-operable controls, readable contrast, labels, and clear status messages.
- **NFR-10 Data integrity:** prevent duplicate/incorrect patient associations and preserve source values separately from derived values.

## 6. Core data entities

### Patient
- `id` — internal RADSAFE Patient ID (primary key).
- `displayCode` — user-facing pseudonymous code.
- `createdAt`, `updatedAt`.
- Optional protected identity fields only if justified and approved.

### PatientIdentifier
- `id`
- `patientId`
- `identifierType`
- `issuer`
- `institutionId`
- `value` (protected; avoid exposing in routine UI)
- `source`

### Examination
- `id`
- `patientId`
- `studyDateTime`
- `institution`
- `stationName`
- `modality`
- `protocolName`
- `anatomicalRegion`
- `sopInstanceUid` (where appropriate)
- `sourceFileHash`
- `parseStatus`
- `createdAt`

### DoseMetric
- `id`
- `examinationId`
- `metricType` (CTDIvol, DLP, etc.)
- `value`
- `unit`
- `scope/context` (e.g., irradiation event or total report)
- `sourcePath` / extraction reference

### DoseEstimate
- `id`
- `examinationId`
- `effectiveDoseValue`
- `unit`
- `kFactor`
- `kFactorSource`
- `kFactorVersion`
- `methodVersion`
- `calculatedAt`
- `validationStatus`
- `warning`

### DrlReference (later)
- `id`, `region`, `protocolCategory`, `metric`, `value`, `unit`, `population`, `source`, `version`, `effectiveDate`.

### AuditEvent
- `id`, `actor`, `action`, `targetType`, `targetId`, `timestamp`, `details`.

## 7. API contract proposal

Exact routes and DTOs must be agreed by backend and frontend before implementation.

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/v1/uploads/rdsr` | Upload and process an RDSR |
| GET | `/api/v1/patients` | Search/list patient records using permitted fields |
| GET | `/api/v1/patients/{id}` | Patient profile |
| GET | `/api/v1/patients/{id}/examinations` | Chronological examination history |
| GET | `/api/v1/examinations/{id}` | Examination details |
| GET | `/api/v1/patients/{id}/dose-summary` | Cumulative dose summary |
| GET | `/api/v1/match-reviews` | Pending uncertain patient matches |
| POST | `/api/v1/match-reviews/{id}/decision` | Resolve a proposed match |
| GET | `/api/v1/health` | Application health check |

## 8. Acceptance criteria for MVP

- A supported de-identified CT RDSR sample uploads successfully.
- Unsupported or malformed files return a safe, understandable error.
- Extracted CTDIvol/DLP values and units match the source report for agreed test cases.
- Effective-dose calculations match independent manual calculations within defined numeric tolerance.
- Every examination is linked to exactly one RADSAFE patient record after match resolution.
- The system does not silently merge uncertain cross-institution identities.
- Patient history is chronological and displays all linked test examinations.
- Cumulative total is reproducible from the included examination records.
- Missing values and estimates are clearly labeled.
- No identifiable real patient data is used in public demos or repositories.

## 9. Open decisions

- Will direct identifiers be stored at all, or will the initial prototype use only pseudonymous test identifiers?
- What retention and access-control policy applies before any real data is handled?
- Which PDF library and report template will be used in the report phase?
